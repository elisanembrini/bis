# Project instructions

## Context

Bis is a web recipe book designed for the phone, for a small group of people who live in the same home. Each person keeps their own recipes (with photos, servings and tags), searches them by name or by ingredient, shares them with the other people in the household and follows them step by step in cooking mode, with timers and voice commands.

Status: features F1 to F9 of the specification are implemented (sign-in, household and invitations, recipes with photos, tags, search, servings, sharing and copying, cooking mode, installable app). The app has not been deployed to production yet.

The full specification is in `docs/SPEC.md`, the visual identity in `docs/DESIGN.md`. The product interface is in Italian.

## Stack

- Backend: Python 3.12, FastAPI, SQLAlchemy 2.x, Alembic, PostgreSQL, Pydantic v2, managed with uv
- Frontend: React with React Compiler, Vite, TypeScript (strict), TanStack Router, Mantine, TanStack Query, Zustand, i18next, managed with pnpm
- Frontend quality: Oxlint (type-aware), Oxfmt, Vitest, Storybook
- Tooling: Docker and Docker Compose, Playwright for e2e tests

## Monorepo structure

```
apps/backend/      FastAPI API, models, Alembic migrations, pytest tests
apps/frontend/     React + Vite app, Storybook configuration in .storybook/
e2e/               Playwright tests
docs/SPEC.md       product specification
docs/DESIGN.md     visual identity
openapi.json       API schema exported by the backend
docker-compose.yml
```

- Do not put shared code outside these folders without asking.
- Any change that touches both backend and frontend is planned as a single task, starting from the backend.

## Commands

Local environment (from the root):

- `docker compose up -d`

Backend (from `apps/backend`):

- Install dependencies: `uv sync`
- Add a dependency: `uv add <package>` (only after approval)
- Tests: `uv run pytest`
- Lint and types: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy .`
- New migration: `uv run alembic revision --autogenerate -m "<description>"`
- Apply migrations: `uv run alembic upgrade head`
- Export the API schema: `uv run python -m scripts.export_openapi` (writes `openapi.json` in the root)

Frontend (from `apps/frontend`):

- `pnpm install`, `pnpm dev`, `pnpm build`
- Lint: `pnpm lint` (runs `oxlint --type-aware`)
- Formatting: `pnpm format` and `pnpm format:check` (run `oxfmt` and `oxfmt --check`)
- Types: `pnpm typecheck` (runs `tsc --noEmit`)
- Unit and component tests: `pnpm test` (runs `vitest run`)
- Storybook: `pnpm storybook`, `pnpm build-storybook`
- Regenerate API types: `pnpm generate:api` (runs `openapi-typescript ../../openapi.json -o src/api/generated/schema.d.ts`)

E2E (from the root):

- `pnpm test:e2e`

## API contract

- The source of truth is the OpenAPI schema generated by the backend.
- The exported schema (`openapi.json`, in the root) is versioned in the repository, so every change to the contract is visible in the diff.
- The TypeScript types are generated by openapi-typescript in `apps/frontend/src/api/generated/schema.d.ts` and must never be edited by hand.
- After every change to Pydantic schemas or routes: export the schema, regenerate the types, run `pnpm typecheck`. Type errors in the frontend point to the places to update.
- Use `response_model` and explicit schemas on every route, so the generated schema is precise.

## Way of working

- Before making a non-trivial code change, propose a plan: files involved, approach, doubts. Wait for confirmation.
- If a request is ambiguous, ask questions instead of making assumptions.
- Work in small steps. After each step run lint, formatting, typecheck and the relevant tests.
- A task is done only when lint, format check, typecheck and tests pass.
- Never disable linter or type checker rules (`noqa`, `type: ignore`, `oxlint-disable`, `@ts-ignore`, `@ts-expect-error`) without explicit approval.
- Do not add dependencies without asking.
- Do not modify migrations that have already been applied: always create a new migration.
- Do not run destructive commands (dropping tables, resetting the database, `rm -rf`, force push) without confirmation.
- If you find existing code that contradicts these rules, report it instead of silently fixing it.

## Backend

- Layered structure: `routers`, `services`, `repositories`, `models`, `schemas`.
- Thin routes: business logic lives in the services.
- Separate Pydantic schemas for input and output. Never expose ORM models in responses.
- Type hints everywhere.
- Domain exceptions handled by a central handler that produces consistent HTTP responses.
- Configuration from environment variables. No secrets in the code.
- Always review autogenerated migrations: Alembic often gets renames, enums and constraints wrong.
- Avoid N+1 queries: load the needed relationships explicitly.
- Tests with pytest on a real PostgreSQL in Docker, not on SQLite.

## Frontend

### Structure

- `src/routes/`: file-based TanStack Router routes. Route files stay thin and delegate to the features.
- `src/features/<feature>/{components,hooks,store}`: logic and components of each feature.
- `src/components/`: UI components reusable across features.
- `src/api/`: typed client and generated types.
- Tests and stories sit next to the file they cover: `Name.test.tsx`, `Name.stories.tsx`.

### General rules

- Strict TypeScript, no `any`.
- UI with Mantine components and a centralized theme. No arbitrary inline styles.
- No hardcoded visible strings: everything goes through i18next, with keys organized by feature. Add every new key in all supported languages (the parity test fails otherwise).
- Anything that depends on the language (date, list and number formats, the speech recognition and synthesis language, the voice-command phrases) comes from i18next or the active `i18n.language`, never from a fixed locale such as `it-IT`.
- Starter data that users see (the starter tags) is identified by a stable key and translated in the frontend; the API returns error codes with English messages and the interface translates from the code.
- Always handle the loading, error and empty-list states.

### React Compiler

- The compiler handles memoization: do not add `useMemo`, `useCallback` or `memo` to optimize, unless there is a measured and approved performance problem.
- Always follow the Rules of React (pure components and hooks, no mutation of props, state or values during render). The compiler skips components that violate them.

### Routing

- The generated route tree (`routeTree.gen.ts`) must never be edited by hand.
- Navigate only with typed `Link` and `useNavigate`. Never URLs built by string concatenation.
- Search params validated with `validateSearch` on every route that uses them.
- Preload data in route `loader`s with `queryClient.ensureQueryData`, using the same query options as the components.

### Data and state

- API calls only through the typed client defined in `src/api/client.ts` (openapi-fetch + openapi-react-query), never hand-written `fetch` calls to the backend.
- To read and write data use `$api.useQuery` and `$api.useMutation`. Do not redefine request or response types by hand: always derive them from `schema.d.ts`.
- Query keys derived from openapi-react-query: to invalidate, use `$api.queryOptions(...).queryKey`, not hand-written keys.
- Server state only with React Query. State in the URL (filters, pagination, tabs) in the router's search params. Zustand only for global client state. Local state with `useState`.

## Tests

- Vitest for unit tests: hooks, utilities, Zustand stores, data transformation logic.
- Storybook for components: every reusable component has stories for its main states (default, loading, error, empty, disabled).
- Stories also run as component tests through Storybook's Vitest integration. Important interactions are verified with `play`.
- Stories use mock data and do not call the backend. The Mantine, i18next and router providers are configured once, as decorators in `.storybook/preview.tsx`.
- Playwright for critical end-to-end flows: authentication, the main flow, the main error cases.
- Selectors based on role, label or text (`getByRole`, `getByLabel`), never on CSS classes.
- Every significant new feature has unit tests for its logic, stories for the new components and at least one e2e test of the main path.

## Minimum security

- Input validation always on the server.
- Authorization checked on every endpoint, not just authentication.
- Authentication uses httpOnly, Secure, SameSite=Lax cookies managed by the backend.
- Never store tokens or session data in localStorage or sessionStorage.
- `.env.example` always up to date, `.env` never in the repository.
